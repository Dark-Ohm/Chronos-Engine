## ЗАДАНИЕ O-10 — Дизайн tiered hot/cold KV-offload (главный трек к 262K)

**Research + design, БЕЗ КОДА.** Дeliverable — дизайн-док
`docs/design/tiered-kv-offload.md` (новый файл, единственная правка в дереве).

### Зачем
Цель проекта: 262144 контекста на RTX 3070 8GB. Замеры (Z-1) и research
(H-10) сошлись: квантизацией KV это не решается — веса Qwythos (5.9GB) +
фон десктопа (1.3–1.9GB) съедают бюджет, на KV остаётся 0.2–0.8GB, а
kvarn2@262K ≈ 1.3GB. Единственный путь без потери качества: hot-tier
(последние 32–64K токенов, kvarn4/turbo3, VRAM) + cold-tier (остальное,
RAM, 64GB DDR4 простаивают) с асинхронным префетчем. PCIe 3.0 x16
(~16GB/s) перекрывает потребность декода с запасом.

### Что изучить (в этом порядке)
1. Наше дерево: как аллоцируется и живёт KV — `src/llama-kv-cache.cpp`,
   `src/llama-kv-cache-kvarn.cpp`, `llama-memory-hybrid.*` (qwythos:
   attention всего в 8 слоях из ~33, KV мал — 596 MiB @ 65536 kvarn4,
   остальное SSM/RS-буфер 201 MiB, его offload НЕ трогаем).
2. Механика `--no-kv-offload` (-nkvo) в нашем дереве: KV целиком в RAM —
   почему это медленно и что из этой инфраструктуры переиспользуемо.
3. Донор `donors/thetom-turboquant`: есть ли там tiering/offload-механика
   (грепай offload/tier/host/pin/prefetch), что переиспользуемо.
4. Наш уже смерженный codacus expert-prefetch (MoE host-pin + префетч
   экспертов): та же идея «горячее в VRAM, холодное в RAM с префетчем» —
   какие куски инфраструктуры (пиннинг, стримы, префетч-хуки) можно
   переиспользовать для KV.

### Дизайн-док должен отвечать
- Структуры данных: как делится KV-буфер на tier'ы, где живут метаданные
  границы hot/cold, что происходит при сдвиге окна.
- Миграция: когда токен уезжает hot→cold, батчами какого размера, в каком
  формате (сразу kvarn-пожатый или fp16).
- Префетч: что тянем cold→hot заранее, каким CUDA-стримом, как
  перекрывается с compute (по образцу codacus expert-prefetch).
- Attend по cold-части: полный attend на 262K каждый токен не влезет по
  bandwidth — какая стратегия (attend только hot + периодический полный?
  heavy-hitters из H2O? честно назови trade-off качества).
- Совместимость с kvarn-ядрами flash-attention (K/V нарезаются группами
  по 128) и с seq_rm=FULL классификацией kvarn.
- CLI: предложи флаги (`--kv-hot-size N` и т.п.).
- Поэтапный план внедрения: фазы с проверяемыми критериями каждая,
  оценка какие файлы трогает каждая фаза.
- Риски и открытые вопросы отдельным списком.

## Приёмка O-10: ПРИНЯТО ✓

Дизайн-док сильный: переиспользование codacus prefetch-инфры подтверждено
мной по дереву (prefetch_backend/slots/events в ggml-backend.cpp), скоуп
чистый (одна правка — док). Честно назван trade-off attend-стратегий.

Поправка Архитектора: Phase 1 (hot-only attend) сама по себе НЕ закрывает
цель «262K без явной потери качества» — это инфраструктурная ступень.
Цель закрывается только Phase 2 (H2O) / Phase 3 (periodic full attend).
В таком виде и планируем.

Ответы на вопросы: (1) --kv-cold-type — да, заложить в дизайн, реализация
не раньше Phase 2. (2) Unified memory — нет, explicit async DMA: твой же
аргумент про page faults верен, плюс codacus-паттерн уже проверен боем.
