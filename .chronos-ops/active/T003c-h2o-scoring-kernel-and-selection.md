## Блокер №0 (первым, до Z-4/T003a/T003b по порядку правки, хоть и не по порядку разблокировки) — SPEC содержит неверную формулу scoring

`docs/design/h2o-heavy-hitters-PHASE2-SPEC.md:47` (секция 1.3) предлагает:

> Reuses the *same* KVarN flash-attention kernel path with a modified
> epilogue that writes `rowsum(softmax(QK^T))` to a side buffer instead
> of reducing into V.

**Это математически бессмысленно как importance score.** `softmax(QK^T)`
для фиксированного query — распределение вероятностей по ключам, оно
**по определению** суммируется в 1 по строке (по измерению ключей) для
любого query, независимо от того, какие ключи реально важны. `rowsum`
здесь тождественно даёт вектор из единиц — ноль информации о том, какой
ключ heavy-hitter.

**Что нужно вместо этого** — масса внимания, полученная КАЖДЫМ ключом,
просуммированная по всем query из observation-окна `W` (не по ключам
одного query, а по query для одного ключа — обратная ось):

```
score[key] = Σ_{query in W} softmax(QKᵀ)[query, key]
```

Затем агрегировать `score[key]` по 128-токенным KVarN-группам (среднее
или сумма — решить и обосновать) — это и есть `h2o_scores` per-group из
T003a.

**Порядок действий:** сначала поправить формулу в самой SPEC
(`h2o-heavy-hitters-PHASE2-SPEC.md:47` и соседний buffer-layout, если
там тоже завязано на rowsum-семантику) — это канонический документ,
из которого кто угодно другой может скопировать ту же ошибку повторно,
если поправить только тикет. T003a уже имеет право редактировать этот
файл (CLI-раздел) — либо расширить его разрешённые файлы на этот
раздел тоже, либо (чище) отдельный docs-only коммит до старта T003c.

- `src/llama-graph.cpp`: узел графа для H2O attention score tracking

  Имя (`ggml_kvarn_h2o_score` или актуальное) сверить со SPEC на момент
  старта. Кернель считает исправленную формулу (column-sum по ключам
  в окне W, не rowsum).
- Heavy-hitter selection + retention логика (новый файл или расширение
  существующего) — какие группы остаются «горячими» после prefill, на
  основе агрегированных per-group `score[key]`.
- Fallback на approach C (K-norm приближение, `‖K_i‖²`), если approach A
  окажется слишком медленным на живых замерах.

## Верификация

- **Quality/PPL — не 262K напрямую.** SPEC (Verification, Phase 2) сама
  требует сравнение с full-attention baseline **на 32K с экстраполяцией**
  (полный full-attention проход на 262K — то самое A1, что сама же SPEC
  отклонила как непрактичный, ~4.5 PFLOPs). Снятая версия тикета
  требовала «PPL в пределах 1% от full-attention на 262K» напрямую —
  внутреннее противоречие с собственным обоснованием SPEC, почему
  выбран approach A вместо A1. Верно: PPL в пределах 1% на 32K с H2O
  retention, экстраполяция на 262K по методике SPEC.
- **PCIe bandwidth и DMA/compute overlap — это T003b, не сюда** (снятая
  версия тикета дублировала эту метрику здесь; она измеряет
  prefetch-инфраструктуру, не scoring-логику).
- Живой NIAH после каждого куска этого среза (не только в конце) — урок
  раунда 6: «не падает» ≠ «работает».
