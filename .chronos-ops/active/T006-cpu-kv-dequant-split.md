# T006 — CPU K/V dequant split: K -> original, V -> rotated (изменение контракта)

**Роль:** `ggml/src/ggml-cpu/ops.cpp` (FA-кернел
`ggml_compute_forward_flash_attn_ext_f16_one_chunk`),
`ggml/src/ggml-turbo-quant.c` (dequant-кернелы), при необходимости
`ggml/src/ggml-cpu/ggml-cpu.c` (type traits, если нужен отдельный
K-вариант `to_float`).
**Приоритет:** P3 — реальный фикс корректности CPU-пути, но путь пока
никем не используется; ВТОРЫМ из тройки (после T007, см. «Зависимости»).
**Источник:** приёмка T002 (Архимаг, 2026-08-15), D-018.
**Зависимости:** T002 принят; T007 принят ПЕРВЫМ (turbo4-нога этого тикета
строится на FWHT, не на Гауссовой QR). Делит файл `ggml-turbo-quant.c` с
T007/T008 — правки одного файла в общем рабочем дереве не параллелить.

## Что было найдено (T002, живой PPL)

```
PPL (-c 128, seed 42):   f16/f16 2.39 (ref)
turbo2/turbo2 4.22   turbo3/turbo3 4.11   turbo4/turbo4 84.66
turbo2/f16    4.22   f16/turbo2    2.40    <- turbo2/3: K бит, V ок
turbo4/f16    2.41   f16/turbo4    95.74   <- turbo4:   K ок, V катастрофа
```

Причина — CPU FA деquantит K и V ОДНИМ `to_float`
(`ggml_get_type_traits(k/v->type)->to_float`, ops.cpp ~8497-8498), а у
turbo-типов K и V должны приходить в РАЗНЫЕ домены (как на CUDA, где два
кернела: `k_turbo*_dequant_f16_inv_fwht` для K -> original,
`k_turbo*_dequant_f16` для V -> rotated). Сейчас:

- turbo2/3 dequant отдаёт rotated -> V корректен (граф un-ротирует выход FA),
  но K против неповёрнутого Q -> KQ неверны.
- turbo4 dequant сам un-ротирует -> K корректен, но V un-ротируется ДВАЖДЫ
  (dequant + графовый inverse-WHT).

## Инвариант (не выдумывать заново)

Граф уже кодирует его правильно и CUDA-симметрично: V хранится rotated ->
dequant отдаёт rotated -> граф `ggml_turbo_wht` (inverse) un-ротирует
выпуклую комбинацию (выход FA). Q в CPU FA никто не ротирует -> значит K
должен приходить original (inv-FWHT). Это конвенция decode-пути CUDA.

## Что сделать

1. Развести K- и V-деquant в CPU FA. Сейчас `to_float` один на оба — это
   изменение КОНТРАКТА, не косметика. Варианты (обосновать выбор):
   (a) отдельный K-вариант `to_float` (например `dequantize_row_turbo*_0_k`)
   и его выбор в FA-кернеле для K; (b) явный флаг домена в dequant-вызове.
   НЕ `if (backend == CPU)` в графе — граф строится до того, как планировщик
   выберет бэкенд, и такой гейт расщепит инвариант по бэкендам (D-018,
   отклонённая альтернатива).
2. По типам (после T007):
   - turbo2/3: K-dequant = plain dequant + inverse-FWHT (сейчас plain, без
     инверсии) -> original; V остаётся plain -> rotated.
   - turbo4: K-dequant = inv-FWHT (уже un-ротирует, но после T007 это FWHT,
     не QR) -> original; V-dequant должен ПЕРЕСТАТЬ un-ротировать -> rotated.
3. TCQ не трогать — это T008 (заглушки -> abort), отдельный контракт.

## Верификация

- Та же матрица PPL, что в T002 (8 комбо, корпус / -c 128 / -s 42 из
  `.chronos-ops/active/t002-cpu/`): критерий приёмки — все восемь комбинаций
  в пределах ~2.4 (реф f16), кроме честной квант-деградации.
- Изоляционные комбо перестают быть асимметричными (это был главный симптом):
  turbo2/f16 ~ f16/turbo2 ~ реф; turbo4/f16 ~ f16/turbo4 ~ реф.
- turbo4/turbo4 перестаёт быть катастрофой (84.66 -> класс квант-деградации);
  f16/turbo4 перестаёт быть катастрофой (95.74 -> ~2.4-3).
- «Честная квант-деградация» turbo4 измерена (T007, `t007-roundtrip`):
  rel-L2 mean 9.5% / max 16.4%, norm ratio 1.0000 без крена — это референс
  для приёмки PPL-критерия, не «на глаз».
- **Финальный критерий связки T006+T007 (обязательный, не опциональный):**
  кэш turbo4, записанный CPU-сборкой, читается CUDA-сборкой с тем же
  PPL-классом (кросс-бэкенд CPU-запись -> CUDA-чтение). Перенесён сюда с
  T007 — на сломанном V (двойная un-ротация) он ничего не доказывает.

## После приёмки

CPU-путь turbo2/3/4 становится CUDA-симметричным по доменам; финальный
PPL-прогон по всей матрице + кросс-бэкенд чтение закрывают связку T006+T007.
