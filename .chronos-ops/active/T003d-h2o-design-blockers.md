## Что есть в коде на самом деле (сверено 2026-08-16, HEAD 6016c5d1f)

Прежде чем решать — фактическая раскладка Phase 1, потому что SPEC
описывает несуществующую:

- **F16 stage — это хвост, а не контекст.** Глубина = `stage_groups`
  (`llama-kv-cache-kvarn.h:222`): для non-SWA `tail_groups + 1` (сток),
  для SWA — `tail_groups`. Порядок 7-9 групп, НЕ `n_ctx`.
- **GPU-кольцо `k_records`/`v_records`** держит сжатые записи. Без
  `--kv-hot-size` его ёмкость рассчитана на все группы до `kv_size`
  (`kvarn.cpp:518`); с `--kv-hot-size` модель подменяется на фейковый
  SWA (`llama_kvarn_apply_hot_window`, `llama-model.cpp:2037`), кольцо
  становится оконным и старые слоты ПЕРЕЗАПИСЫВАЮТСЯ.
- **`host_cold_k/v_records` — write-through, только на экспорт.**
  Пишется через `enqueue_cold_offloads` -> `offload_group_to_host`
  (`kvarn.cpp:1036/1063`). Обратно для attend НЕ читается. Пути
  promotion cold->hot нет.
- **`view()` — ОДИН источник.** `kvarn.cpp:1397` — единственный вызов
  `ggml_kvarn_view` по `layer.k_records`/`v_records` со `stage_groups`.
  Никакого prefetch-слота нет: prefetch — это T003b, он не написан.
- **Поля `hot_boundary` не существует.** Оно есть только в design-доках
  Phase 1 и в строке SPEC:186 «Already exists» — это ложь.
- **`flush_hot_to_cold()` не существует.** См. реальные имена выше.

## Блокер 1 — откуда scoring берёт K/V и где живут H2O-группы

**Что говорил SPEC:** prefill «fills F16 stage up to n_ctx» (§4.1),
кернель читает «Q/K/V already in VRAM, F16» (§1.3), H2O-группы «stay in
VRAM F16 stage» (§2.3), hook «No code change needed» (§5.5).
Всё четыре — неверны относительно раскладки выше.

### РЕШЕНИЕ 1.1 — scoring инкрементальный, во время prefill

Скоринг **накапливается**: каждый ubatch prefill добавляет свою массу
внимания ко ВСЕМ группам, которые в этот момент ещё живут в F16-стейдже.
Когда группа уходит из стейджа в сжатую запись, её скор **замораживается**
(больше не обновляется), а не снимается одним кадром.

Формулировка «скорится один раз, в момент ухода» НЕВЕРНА и запрещена:
один кадр на флаше — это внимание последнего ubatch, а не H2O.

**Горизонт метрики — глубина стейджа, а не весь суффикс.** Группа
накапливает массу от запросов, пришедших за время её жизни в стейдже
(`stage_groups`, порядок 1K токенов «будущего»), а не от всего остатка
промпта, как у Zhang et al. Называть это в SPEC ровно так —
**«H2O с горизонтом стейджа»** — и нигде не выдавать за полный
кумулятивный H2O.

ОТКЛОНЕНО: «скорить в конце prefill до вытеснения» — к концу prefill
вытеснять уже нечего, старшие группы давно сжаты; это была та же ложь,
что и в SPEC §4.1.
ОТКЛОНЕНО: читать сжатые записи из RAM через prefetch-слот — механизма
нет (T003b), и он не должен быть предусловием scoring'а.
ОТКЛОНЕНО: второй проход prefill ради «правильного» окна — удвоение
самой дорогой фазы ради метрики отбора.

### РЕШЕНИЕ 1.2 — следствие: метрика H2O-кумулятивная, НЕ SnapKV

Инкрементальный scoring физически не может использовать observation
window SnapKV: в момент прохода группы G последние токены промпта ещё не
существуют. Поэтому берём **исходную H2O-метрику** (Zhang et al.,
accumulated attention score): накопленная масса внимания от всех запросов,
прошедших через данную группу, суммируется по мере prefill.

Это не компромисс, а устранение противоречия: SnapKV требует пост-фактум
взгляда назад из окна, которого у нас нет; H2O-метрика по построению
инкрементальна. Все упоминания SnapKV/observation window из §1.2/§1.3
SPEC убрать, а не «поправить».

### РЕШЕНИЕ 1.3 — H2O-группы удерживаются в СЖАТОМ GPU-кольце, не в F16

Персистентно жить в F16 они не могут: стейдж — позиционный хвост
фиксированной глубины, а не хранилище. Поэтому H2O — это **пин против
перезаписи в кольце records**: выбранные группы не отдаются под
перезапись при wraparound оконного кольца, остальные вытесняются как
сейчас.

Следствия, важные для тикетов:
- **Сам вызов** `ggml_kvarn_view` остаётся односточниковым — но правки
  в read-пути НУЖНЫ, и «No code change needed» из §5.5 неверно.
  Меняется live-set: `mat_idxs` / `n_kv` / ячейки метаданных обязаны
  тащить запиненные группы, лежащие ЗА пределами SWA-окна. Иначе пин в
  кольце бесполезен — кернель просто не спросит эти записи.
- T003b (prefetch) перестаёт быть предусловием T003c. Порядок
  T003a -> T003c допустим; T003b становится независимым слоем.
- Качество H2O-групп ограничено битностью записи, а не F16. Это честная
  цена; заявлять «H2O-группы в F16» в SPEC больше нельзя.
- Нужен бюджетный потолок: пин уменьшает эффективное окно. Число
  H2O-групп ограничить долей ёмкости кольца (конкретное значение — в
  SPEC, дефолт консервативный), и при исчерпании — не пинить.

## Блокер 2 — per-layer selection против глобальных flags

**Противоречие:** `h2o_group_scores` per-layer (`max_groups x n_layers`),
selection per-layer, а `h2o_group_flags` — глобальный (`max_groups`).
Слои выбирают РАЗНЫЕ группы; в один общий bitmask это не пишется.

### РЕШЕНИЕ 2 — flags тоже per-layer: `max_groups x n_layers`

Межслойная редукция (max/mean/majority) отклонена: она уничтожает ровно
тот сигнал, ради которого H2O и делается — разные слои смотрят на разное.
Стоимость per-layer bitmask ничтожна (биты на группу на слой), а кольцо
records и так живёт per-layer (`layer.k_records`), так что пин
естественно ложится на ту же гранулярность.

T003a аллоцирует поле формы `[max_groups][n_layers]` (или упакованный
эквивалент) — НЕ глобальный вектор.

## Блокер 3 — маскирование и редукция 16 Q-heads -> 4 KV-heads

### РЕШЕНИЕ 3.1 — маска: причинность по построению, `causal=false` убрать

Вопрос «causal=false по всем ключам» снимается решением 1.2: кумулятивная
H2O-метрика накапливается из уже посчитанного причинного внимания prefill,
где каждый запрос и так видит только свой префикс. Отдельного
scoring-пасса с собственной маской нет, значит нет и дыры «окно голосует
само за себя». Формулировки «against all keys» и `causal=false` из
§1.2/§1.3 удалить.

### РЕШЕНИЕ 3.2 — GQA: сумма Q-голов внутри KV-группы

16 Q-heads -> 4 KV-heads сворачиваются **суммой** по Q-головам,
относящимся к одной KV-голове (масса внимания аддитивна; mean отличается
константой и теряет смысл «сколько всего пришло»). Скоры хранятся
per-KV-head.

Итоговая форма буфера — `[n_kv_heads][max_groups][n_layers]`, и это
ЕДИНСТВЕННЫЙ контракт: три разных формы в §1.3 (буфер на 4 головы, смета
FLOPs на 16 голов, сигнатура кернеля `[n_heads, n_tokens]`) свести к нему.

**Скоры per-KV-head, флаги per-group — переход между ними:** скоры
группы суммируются по KV-головам, и top-K берётся уже по этой сумме,
внутри слоя. То есть `[n_kv_heads][max_groups][n_layers]` -> сумма по
головам -> `[max_groups][n_layers]` -> top-K на слой -> биты флагов
`[max_groups][n_layers]`. Без этой фразы T003a снова аллоцирует вслепую.
