# T008 — TCQ-CPU: abort вместо тихих нулей (стоп-кран до Viterbi)

**Роль:** `ggml/src/ggml-turbo-quant.c` (TCQ-заглушки quantize/dequant).
**Приоритет:** P2 — дёшево и убирает тихую порчу, которую пользователь не видит.
**Источник:** приёмка T002 (Архимаг, 2026-08-15), D-018.
**Зависимости:** T002 принят. По коду независим от T006/T007, но делит файл
`ggml/src/ggml-turbo-quant.c` — правки одного файла в общем рабочем дереве не
параллелить; ставить после T007/T006 либо отдельным safety-коммитом.

## Что было найдено (T002)

`quantize_row_turbo{2,3,4}_tcq_ref` — заглушки: считают norm, `memset(qs, 0, ...)`
(33/49/65 байт), Viterbi не реализован. `dequantize_row_turbo{2,3,4}_tcq` пишут
литеральные нули. На CPU TCQ нефункционален ВООБЩЕ — не «нет фичи», а
детерминированный мусор: пользователь получает нулевой KV без единого
предупреждения (тихая порча — тот же класс бага, что стоил раунда 6, Z-3/Z-4).

## Что сделать

1. Заглушки обязаны падать с внятным `GGML_ABORT`, а не отдавать нули:
   `GGML_ABORT("turbo*_tcq: no CPU implementation (Viterbi pending)")` в
   `quantize_row_turbo*_tcq_ref` и `dequantize_row_turbo*_tcq` (макрос из
   ggml-impl.h; убедиться, что include на месте).
2. Подтвердить, что abort не задевает CUDA-путь: на CUDA TCQ исполняется
   кернелами (set-rows.cu Viterbi / fattn getrows), а CPU-заглушки
   вызываются только CPU-бэкендом. Если диспетчер может попасть в
   CPU-заглушку на CUDA-сборке (offload-пробел и т.п.) — закрыть и это:
   abort должен срабатывать только на честном «CPU без CUDA».
3. Реализацию Viterbi на CPU в этом тикете НЕ делать — отдельный большой
   тикет. Здесь только стоп-кран.

## Верификация

- CPU-сборка, любой TCQ-тип (CLI-имена `turbo2_tcq` / `turbo3_tcq` /
  `turbo4_tcq`, whitelist common/arg.cpp:318-320): вместо нулей/мусора —
  явный `GGML_ABORT` с сообщением, ненулевой rc.
- CUDA-сборка с TCQ: поведение не изменилось (кернельный путь жив) — regression
  при наличии GPU.
