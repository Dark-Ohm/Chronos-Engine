# T009 — prompt-cache: частичное совпадение молча выбрасывает кэш (не turbo-специфично)

**Роль:** `tools/completion/completion.cpp` (ветка загрузки сессии, ~345-397),
`src/llama-context.cpp` (`llama_memory_seq_rm`, ~3896), реализации `seq_rm`
в `src/llama-kv-cache*.cpp` / `src/llama-memory-*.cpp` — какая именно из них
работает у Qwythos-9B-MTP, предстоит установить.
**Приоритет:** P3 — не корректность вычислений, а тихая потеря
производительности + вводящее в заблуждение сообщение.
**Источник:** кросс-бэкенд прогон T006+T007 (Архимаг, 2026-08-15),
`.chronos-ops/active/T006-T007-crossbackend-report.md`.
**Зависимости:** нет. С T006/T007/T008 не пересекается по файлам.

## Что найдено

При `--prompt-cache FNAME --prompt-cache-all` сохраняется промпт + сгенерированные
токены. На следующем запуске с тем же (более коротким) промптом:

```
llama_completion: session file has exact match for prompt!
llama_completion: unable to reuse common prefix (for example, when the memory is recurrent)
```

Механика — `completion.cpp:372-378`: если `session_tokens.size() > n_match`,
вызывается `llama_memory_seq_rm()` для удаления «будущих» токенов; он
возвращает false -> `llama_memory_clear(mem, true)`, `session_tokens.clear()`,
`n_match = 0` -> **весь промпт пересчитывается заново**, кэш выброшен.

Пользователь при этом видит бодрое `exact match for prompt!` строкой выше и
никакого указания на то, что кэш не использован. Ровно на этом чуть не
проехал кросс-бэкенд тест: логи выглядели зелёными, а проверяемого события
не происходило.

**Атрибуция проверена, а не предположена.** Первая гипотеза «turbo-KV не
переживает seq_rm» ОПРОВЕРГНУТА контролем: `-ctk f16 -ctv f16` даёт тот же
результат. Значит причина не в turbo-типах и это НЕ родственник
`iq4_nl`-whitelist (T001) или llama-bench-гэпа.

## Что сделать

1. **Назвать корневую причину, не угадывать.** Установить, какая реализация
   `seq_rm` отрабатывает для Qwythos-9B-MTP (кандидаты: `llama_memory_hybrid`,
   `llama_memory_recurrent`, `llama_kv_cache_dsv4`, `_dsa`, `_kvarn`,
   `_iswa` — последняя возвращает `res_base & res_swa`, то есть false от
   любой половины). Доказать логом/отладчиком, какая ветка даёт false.
2. Проверить, ограничение это принципиальное (для recurrent-состояний
   частичное удаление действительно невозможно) или дефект гейта, как было
   с `seq_rm` в сервере (`df7e25a89`).
3. Сообщение сделать честным: назвать тип памяти и прямо сказать
   «кэш сброшен, промпт будет пересчитан полностью». Текущая формулировка
   «for example, when the memory is recurrent» — гадание вслух, а не диагноз.
4. Если ограничение принципиальное — задокументировать в README/доке по
   prompt-cache: `--prompt-cache-all` на таких моделях бесполезен, кэш
   переживает только полное совпадение.

## Верификация

- Воспроизведение до фикса: turbo4 И f16 -> обе дают `unable to reuse`.
- После фикса (или после документирования): сообщение называет причину и
  фактическое последствие; если гейт чинится — вторая ветка
  `completion.cpp:389` (replay) отрабатывает и на частичном совпадении.
- Регресс: полное совпадение промпта продолжает работать
  (`replayed last token from session`, кэш используется) — это тот путь,
  на котором стоит кросс-бэкенд тест T006+T007, ломать его нельзя.

## Заметка на будущее

В любой харнесс, проверяющий кэш, вшивать проверку «кэш использован, а не
просто открыт» (`replayed >= 1 && wiped == 0`). Без неё тест зелёный и пустой.
Пример — `.chronos-ops/active/t006-cross.sh`.
