## Приёмка O-1 — ОТКЛОНЕНО, критический баг в пункте 1

Пункт 2 (plain non-SWA ветка) и пункт 3 (hybrid_iswa — верно не трогал) —
норм, сигнатура `llama_kv_cache_kvarn` сверена и совпадает.

Пункт 1 (два вызова `llama_kv_cache_iswa`) — СЛОМАН. Смотри фактический
файл, src/llama-model.cpp:2200-2247 СЕЙЧАС:

```cpp
if (arch == LLM_ARCH_GEMMA4_ASSISTANT) {
    ...
    res = new llama_kv_cache_iswa(..., mem_other, ..., share, params.kvarn);
    res = new llama_kv_cache_iswa(..., nullptr,   ..., share, params.kvarn);
}
```

Закрывающая `}` и `} else {` МЕЖДУ этими двумя вызовами ИСЧЕЗЛИ. В диффе
это видно прямо: `share);` + `} else {` → `share,\n params.kvarn);` —
`} else {` не воспроизведена, просто выпала. Последствия:

1. Для `LLM_ARCH_GEMMA4_ASSISTANT`: два `new` подряд без `else` — первый
   (с `mem_other`, ради которого вообще существует эта ветка) утекает,
   `res` в итоге указывает на ВТОРОЙ (с `nullptr`) — Gemma4-assistant
   cross-context share сломан + утечка памяти на каждое создание.
2. Для ЛЮБОЙ ДРУГОЙ архитектуры с `swa_type != LLAMA_SWA_TYPE_NONE`
   (подавляющее большинство SWA-моделей, не только kvarn) — второй `new`
   (который раньше был веткой `else`, то есть общим случаем) теперь
   вложен ВНУТРЬ `if (arch == LLM_ARCH_GEMMA4_ASSISTANT)` и для них
   вообще не выполняется. `res` остаётся неинициализированным — создание
   KV-кеша для всех обычных SWA-моделей сломано целиком, это не
   kvarn-specific регресс, а поломка базового пути.

Скорее всего результат неаккуратного multi-line замены (добавляли
`params.kvarn` в конец обоих вызовов и задели структурную скобку между
ними). Диффстат/отчёт этого не показал — впредь после правки с добавлением
хвостового аргумента в несколько соседних вызовов проверяй фигурные скобки
вокруг руками, не только сам факт "аргумент добавлен".

**Фикс:** верни структуру как было — оставь `res = new llama_kv_cache_iswa(...)`
с `mem_other` внутри `if (arch == LLM_ARCH_GEMMA4_ASSISTANT) { ... }`, ЗАКРОЙ
этот if через `} else {`, и вызов с `nullptr` (общий случай) — в этой
else-ветке. Оба вызова получают `params.kvarn` последним аргументом как и
было (это единственное, что было нужно менять) — просто верни `} else {`
между ними. Отчитайся diff'ом ПОСЛЕ фикса, отдельно подтверди, что
`} else {` на месте.

## ЗАДАНИЕ O-3 — DSv4: убрать неявный UB-инвариант в static_cast

Из накопленного списка гэпов (HANDOFF): `src/llama-kv-cache-dsv4.cpp`

(llama-kv-cache-dsv4.cpp:975-977, единственное место конструирования)

не передаётся вообще, дефолт `llama_kvarn_default_params()`). Т.е.
инвариант "kv_raw никогда не kvarn" сейчас держится, но он НИГДЕ явно не
закреплён — молчаливо сломается, если кто-то потом передаст kvarn в этот
конструктор (например, при активном DSv4+kvarn use-кейсе в будущем).

Задача: не менять логику, а сделать инвариант явным — assert вместо тихого UB.

### Точки

```cpp

```
(имя переменной/метода get_base vs get_swa — по месту, сохрани

## Приёмка O-3 — ОТКЛОНЕНО. Файл структурно разрушен, отчёт не соответствует диффу.

Это НЕ баг уровня «пропущенная скобка» (O-1/O-2). Это разрушение структуры
файла. Смотри `git diff -- src/llama-kv-cache-dsv4.cpp` и код СЕЙЧАС,
:1421-1478, реально:

```cpp
llama_kv_cache_dsv4_raw_context::llama_kv_cache_dsv4_raw_context(llama_kv_cache_iswa * kv) :
    kv_swa([&]() { ... }()),
    ctx_base_mem(nullptr),
    ...
}

    kv_swa([&]() {                              // <- ГОЛЫЙ ЧЛЕН-ИНИЦИАЛИЗАТОР
        ...                                      //    ВНЕ какого-либо конструктора,
    }()),                                        //    прямо в теле файла между функциями
        llama_kv_cache_iswa * kv,               // <- параметр функции ЗДЕСЬ, после
                llama_kv_cache_context(          //    member-init-списка предыдущего блока
                    [&]() { ... }(), std::move(sinfos_base_write), this->ubatches_write)),
        bool optimize) :                        // <- сигнатура конструктора
    kv_swa([&]() { ... }()),                     //    ЗАКРЫВАЕТСЯ здесь, но её начало
    ctx_base_mem(kv->get_base()->init_update(lctx, optimize)),  // <- lctx НИГДЕ не объявлен,
    ...                                          //    параметр llama_context * lctx ИСЧЕЗ
```

Три конкретных вида поломки:

1. **Второй конструктор `(llama_kv_cache_iswa*, llama_context*, bool)` лишился
   параметра `llama_context * lctx`** — строка `llama_context * lctx,`
   заменена твоей заменой `static_cast`, хотя это была ОБЪЯВЛЕНИЕ ПАРАМЕТРА,
   а не static_cast-выражение. Тело конструктора всё ещё зовёт `lctx` —
   не соберётся вообще (undeclared identifier).
2. **Инициализатор `kv_swa(...)` теперь стоит СНАРУЖИ любого конструктора**
   (после закрывающей `}` первого конструктора, до объявления сигнатуры
   второго) — это не валидный C++ ни при какой интерпретации, голый
   выражение-с-запятой на уровне namespace.
3. **Третий конструктор содержит ДВА `ctx_base_mem(...)` инициализатора**
   (один — твоя вставка с лямбдой, второй — исходный с уже применённой
   заменой) — member-init-list с одним и тем же членом дважды тоже не
   компилируется, плюс `sinfos_read(std::move(sinfos_swa_read))` пропал.
4. Свободная функция `dsv4_build_full_sinfo` (НЕ конструктор, НЕ класс)
   получила `kv_swa([&](){...}()),` ВМЕСТО строки `sinfo.resize(n_stream);`
   — это переменной `kv_swa` в этой функции не существует, синтаксис
   member-initializer в теле обычной функции невалиден.

Похоже на автоматическую замену по текстовому паттерну
`static_cast<llama_kv_cache *>(...)`, которая задела совпадения ВНЕ их
реального контекста (объявления параметров, member-init-lists на несколько
строк, свободные функции) и перемешала соседние строки. Отчёт при этом
описывает результат как «7 точечных замен, лямбды сохраняют существующую
структуру» — это НЕ совпадает с фактическим диффом ни в одной из этих
4 точек. Три подряд инцидента с недостоверным отчётом (О-1 не считаю тем
же классом — там ошибка была реальной, но отчёт хотя бы описывал то, что
было в коде; здесь отчёт описывает код, которого в диффе просто нет).

### Требую

1. **Полный откат файла**: `git checkout -- src/llama-kv-cache-dsv4.cpp`
   (или эквивалент) — не пытайся патчить поверх текущего месива, это
   гарантированно оставит мусор.
2. **Переделать вручную, по одному месту за раз**, БЕЗ автоматических
   текстовых замен по паттерну. Для каждого из 7 (или сколько реально
   есть) `static_cast<llama_kv_cache *>` — сначала прочитать ВЕСЬ
   охватывающий блок (весь конструктор целиком, от сигнатуры до закрывающей
   `}` тела, включая member-init-list), понять, стоит ли cast в
   member-init-list (там нужен IIFE-лямбда паттерн, как ты и придумал —
   идея верная) или в теле функции (там можно просто 2 строки:
   `auto * x = dynamic_cast<...>(...); GGML_ASSERT(...)`, лямбда не нужна).
3. Для СВОБОДНОЙ функции `dsv4_build_full_sinfo` (:1398, принимает
   `const llama_kv_cache * kv`, а не `llama_kv_cache_iswa *`) — эта функция
   ВООБЩЕ не должна была попасть в список замен, в ней нет
   `static_cast<llama_kv_cache *>` в исходнике (проверь ещё раз, что там
   было ДО твоей правки — верни как было, если это не входило в
   оригинальный grep-список).
4. После переделки — вставь в отчёт **полный текст каждой изменённой
   функции целиком** (не таблицу "строка X -> строка Y", а весь блок от
   сигнатуры до `}`), плюс `grep -c` до/после, плюс баланс `{`/`}` и `(`/`)`
   по всему файлу (оба вида скобок в этот раз, не только один).
5. Прежде чем писать отчёт — перечитай сам файл целиком с начала
   конструктора до конца, как будто ты компилятор.

Не спеши. Лучше один раз медленно и правильно, чем третий раунд правок.
