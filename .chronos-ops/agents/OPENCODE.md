# OPENCODE — Рабочий журнал

Этот файл пишет ТОЛЬКО Архитектор. Файл держит ТОЛЬКО текущее задание —
история в `git log -- .chronos-ops/OPENCODE.md`. Отчёты — ТОЛЬКО в
`opencode-report.md` рядом (перезаписывай: номер задания, diffstat,
пропущенное с причинами, вопросы).

## ПРАВИЛА ИСПОЛНИТЕЛЯ (обязательны)

1. **Нет разрешения на инструмент — значит НЕТ.** Уперся — СТОП, строка в отчёт.
2. **Сборку и тесты запускает Архитектор.** cmake/ctest/gdb не трогать.
3. **Скоуп задания — граница.** Молчаливый выход за скоуп = откат.
4. Не коммитить. Коммитит Архитектор после приёмки.
5. Никаких regex/sed-замен по нескольким вхождениям разом в C++-коде.
6. «Взять файл целиком из донора» ЗАПРЕЩЕНО — только адресные правки.

### Зачем именно "первый срез"
Полная реализация (kernel + graph node + scoring pass) — большой кусок.
Этот раунд — только структуры данных и CLI-проводка, ПО ОБРАЗЦУ Z-2:
строго opt-in, весь новый код инертен без флага. Кернел и граф-узел —
следующее задание, после того как эта проводка проверена и принята.

### Что сделать (по SPEC §5, пункты 1-3 и 6 из списка хуков)
1. **Поля в `llama_kv_cache_kvarn`** (`src/llama-kv-cache-kvarn.h`):
   - `h2o_group_flags` — какой тип выбрать (bitmask/bool-массив, размер
     = max_groups) сам реши и обоснуй в отчёте;
   - `h2o_scores` — per-group средний скор (float, размер = max_groups
     × n_layers либо per-layer массив — сверь, как у нас организованы
     per-layer данные в этом классе, не выдумывай новую схему);
   - `h2o_groups` — количество групп, аналог `kv_hot_size` у Z-2 (0 =
     выключено).
   Следуй уже существующему паттерну Z-2: `const uint32_t h2o_groups;`
   в списке членов, производный `const bool h2o_enabled;` гейт — по
   образцу `cold_offload` (`llama-kv-cache-kvarn.h:229`, `.cpp:519`).
2. **CLI-флаг `--kv-h2o-groups N`** — зеркалируй `--kv-hot-size` один в
   один: `common/arg.cpp` (парсинг + округление, если нужно — но группы,
   не токены, свериться с SPEC §3, единица измерения ГРУППЫ, не токены),
   `common/common.h`, `common/common.cpp`, `include/llama.h`,
   `src/llama-cparams.h`, `src/llama-context.cpp`, проводка через
   `llama-model.cpp` до ctor `llama_kv_cache_kvarn` (те же call-site'ы,
   что `kv_hot_size` — `llama-model.cpp:2159`/`:2287` на сегодняшнем HEAD,
   проверь по факту, номера могли сдвинуться).
3. **НЕ делать в этом задании** (следующий раунд): сам scoring-кернел
   (`ggml_kvarn_h2o_score`), граф-узел (`build_h2o_scores`), любую логику
   выбора top-K групп, любые изменения в flush/store-путях кроме самого
   поля. Если поле `h2o_group_flags` физически некому писать в этом
   задании — это нормально, оно просто всегда пусто/false, как и
   задумано для чистого плюмбинга.

### Границы
- Файлы: `src/llama-kv-cache-kvarn.h`, `common/arg.cpp`, `common/common.h`,
  `common/common.cpp`, `include/llama.h`, `src/llama-cparams.h`,
  `src/llama-context.cpp`, `src/llama-model.cpp`. Ничего в
  `llama-graph.cpp/.h`, `llama-kvarn.*`, `ggml-cuda/` — это следующий
  раунд.
- `llama-kv-cache-kvarn.cpp` — можно, только для конструктора (инициализация
  новых полей), не для логики store/flush/view.

### Критерий «готово к сборке»
- Компилируется по твоей оценке.
- Без флага `--kv-h2o-groups` (или 0) — поведение идентично текущему
  (h2o_enabled false, поля не аллоцируются/не используются).
- С флагом — сервер должен просто ПОДНЯТЬСЯ (поле есть, ничего с ним не
  делается активно) — не обязан ничего давать функционально, это чистая
  подготовка почвы.
