## Метод замера (живой)

Временная env-гейтированная инструментация в `offload_group_to_host`
(зона тикета): FNV-1a хэш каждой скопированной K/V-записи группы на все
8 слоёв. Qwythos-9B, `--kv-hot-size 512` (кольцо R = 4 группы), промпт
2330 токенов (16 групп), `-ub 256`. Три прогона:
- **до фикса, `-b 2048` (дефолт сервера)** — копии испорчены;
- **`-b 256`** (каждый llama_decode <= 1 ubatch) — все копии различны;
- **после фикса, `-b 2048`** — все копии различны.

Критерий корректности: у каждой группы ровно одна запись на слой; слот
кольца `g % R` поочерёдно держит разные группы, поэтому «запись группы g
== записи группы g'» при g != g' доказывает, что копия прочитала не свой
слот (stale-захват при коротком лаге или wraparound-перезапись).

## Вердикт (а) — `tail_groups`-лаг: ПОДТВЕРЖДЁН

Чтение CUDA-ядер (`ggml/src/ggml-cuda/kvarn.cu`):
- `kvarn_store_direct_flush_kernel` (:1039): флаш группы `g` срабатывает
  на ПЕРВОМ токене группы `g + tail_groups` (`flush_group = group - tail_groups`,
  guard `group <= tail_groups`).
- `kvarn_store_workspace_flush_kernel` (:1259): та же семантика
  (`flush_group = boundary_group - tail_groups`, guard тот же).
- CPU-путь (`ggml-cpu.c:2315`): no-op proxy — KVARN_STORE нативно только
  на CUDA; cold offload требует `offload=true`, так что CPU-ветка для
  него нерелевантна.

Enqueue (`enqueue_cold_offloads`) ставит группу `g` в очередь при
`seen >= (g + tail_groups + 1) * 128` — на ОДИН полный батч-групп ПОЗЖЕ
точки флаша. Лаг консервативен по построению (запас >= 1 группа).
Живое подтверждение: при своевременном дренаже (прогоны 2 и 3) все 128
копий различны — ни одного stale-захвата (иной слот держал бы данные
другой группы -> дубликат).

## Вердикт (б) — wraparound: потеря РЕАЛЬНА, «avoids in practice» ложно

**Корень (найден чтением + подтверждён замером):** дренаж
`apply_pending_cold_offloads` происходил ТОЛЬКО из
`llama_context::memory_update()` — в начале КАЖДОГО llama_decode.
Контексты decode-цикла (`init_batch`, `init_kv_batch` — гибридный путь
Qwythos) создавались БЕЗ `update_lctx`, и их per-ubatch `apply()`
возвращался раньше времени (`if (!update_lctx) return true;`). Поэтому
внутри одного llama_decode, охватывающего больше групп, чем кольцо,
слот `g % R` перезаписывался флашем группы `g + R` ДО дренажа, и копия
читала чужую запись. Механизм в комментарии («wrap before the next
llama_decode drains») описывает это верно по эффекту, но не по механизму:
дренаж не per-ubatch, а per-decode.

**Живое воспроизведение (до фикса, `-b 2048`):** все копии, кроме групп
14/15 (случайно совпали со своими слотами), содержат записи ПОЗДНИХ
групп: `host[0] == host[4] == host[8] == host[12]` (слот 0 = запись
группы 12), `host[1] == host[5] == host[9] == host[13]` (слот 1 = группа
13) и т.д. 10 пар дубликатов из 16 групп. Триггер — дефолтная
конфигурация сервера: `-b 2048` -> один llama_decode на промпт > ~512
токенов при hot 512.

**Граница (зафиксирована; общий инвариант по уточнению Архитектора):**
копия группы `g` безопасна, если флаш перезаписи `g + R` (токен
`(g+R+tail)*128`) позже копии, а окно enqueue->copy — не больше одного
ubatch. Условие: **`R > 1 + ubatch_groups`**. С формулой кольца
`R = visible - tail + in_flight - 1` и `in_flight = ubatch_groups`
(контигуальный ubatch) члены ubatch сокращаются: гейт сводится к
`visible > tail + 2` — то есть к самому hot-окну, независимо от размера
ubatch. Для SWA (tail = 2): **hot >= 512 безопасно при любом ubatch**
(запас 1 группа), hot = 384 — ровно на границе (небезопасно в худшей
выкладке), hot <= 256 теряет копии даже с per-ubatch дренажем. Замер
проводился при `-ub 256`; формула выше — общий случай. Принудительный
кламп/варн в ctor — отдельный хвост, не в этом тикете.

## Фикс (в зоне тикета, ctor не тронут)

`src/llama-kv-cache-kvarn.h/.cpp` — дренаж переведён на per-ubatch:

- Новый член `llama_context * update_lctx = nullptr;` в
  `llama_kv_cache_kvarn` (`llama-kv-cache-kvarn.h`, рядом с `h2o_*`).
- `init_update(lctx, ...)` запоминает `update_lctx = lctx`
  (decode-путь всегда вызывает init_update перед init_batch/init_kv_batch).
- `init_batch(...)` и `init_kv_batch(...)` (гибридный путь Qwythos!)
  передают `update_lctx` в контекст — per-ubatch `apply()` из
  `process_ubatch` теперь дренит (sync + копии) после каждого ubatch.
- Комментарий `enqueue_cold_offloads` переписан: лаг помечен VERIFIED
  (дата, метод), wraparound-абзац заменён описанием фикса и остаточной
  границы.

Почему этого достаточно: между enqueue (build ubatch k) и копией (apply в
начале ubatch k+1) выполняется граф ТОЛЬКО ubatch k — кольцо продвигается
<= 1 ubatch, а перезапись слота `g` приходит через `R - 1 >= 2` группы
после точки enqueue (hot 512). Группы, enqueue-нутые в последнем ubatch
decode, копируются дренажем следующего llama_decode — тоже до перезаписи.

## Верификация (живая, после фикса)

| Прогон | Результат |
|---|---|
| До фикса, `-b 2048` | 10 дубликатов пар из 16 групп — копии испорчены |
| `-b 256` (до фикса) | Все 128 копий различны — лаг корректен при своевременном дренаже |
| После фикса, `-b 2048` (бывший сломанный) | Все 128 копий различны — потеря устранена |
| После фикса, `-b 256` | Все 128 копий различны — регресса нет |
| Без флага (после фикса) | Сервер поднимается, генерация идёт, копий нет (`pending` пуст) |

Дренаж действительно per-ubatch (проверено по логу): копии групп 0-11
идут в течение первого llama_decode (2048 токенов, 6+ дренажей подряд),
12-13 — дренажем второго decode, 14-15 — внутри третьего.

## Что осталось для Архитектора

1. **Остаточная граница hot <= 384 токенов**: при таком окне кольцо
   меньше окна enqueue->copy одного ubatch, копии теряются даже с
   per-ubatch дренажем. Полный фикс = увеличение кольца (смена layout /
   state-версии) — за пределами зоны тикета. Рекомендация: предупреждение
   или кламп hot-окна >= 512 при включённом cold offload (ctor — вне зоны,
   не трогал).
2. **Цена фикса**: +1 `llama_synchronize` на ubatch во время prefill с
   cold offload (только когда очередь непуста). Для prefill приемлемо;
   T003b при построении prefetch-слотов может пересмотреть.
3. Для T003c: пин — в GPU-кольце records (T003d), `host_cold_*` на attend
   не читается; гейт снят, потому что wraparound понят и host-путь больше
   не врёт. Сам пин — работа T003c, этот тикет его не делает.
