## ЗАДАНИЕ Z-2 — Phase 1 tiered hot/cold KV-offload (реализация)

Реализуешь Phase 1 по принятому дизайну `docs/design/tiered-kv-offload.md`
(O-10, принят). Дизайн — канон; отступление от него = сначала строка в
отчёте, потом код. Прочитай также ARCHITECTURE.md «Принятые решения
раунда 4» и D-011/D-014 в DECISIONS.log.

### Скоуп (строго Phase 1 из дизайна)
1. `src/llama-kv-cache-kvarn.h/.cpp`: host-pinned cold-буферы
   (`host_cold_k_records`/`host_cold_v_records`), поле `hot_boundary`,
   store-путь пишет compressed records в host-буфер при переполнении
   hot-стейджа (граница выровнена по группам 128).
2. `src/llama-kvarn.h/.cpp`: хелпер копирования record→host
   (async DMA, по образцу codacus: `ggml_backend_tensor_set_async` +
   event; см. `ggml-backend.cpp` prefetch_* — НО в Phase 1 сам
   prefetch cold→hot НЕ делаем, только выгрузку hot→cold).
3. CLI/params: `--kv-hot-size N` (кратно 128, дефолт 512) →
   `common/arg.cpp` → `llama_context_params` → проводка до kvarn-кеша
   (`llama.h`, `llama-context.cpp`, `llama-model.cpp`).
4. Attend в Phase 1 — только hot-окно (как в дизайне). Cold-данные
   сохраняются, но не читаются (инфраструктура для Phase 2/3).
5. seq_rm: cold-группы инвалидируются через метадату (D-011: kvarn=FULL,
   полное снятие seq — host-буфер просто помечается мёртвым).

### Границы
- `ggml-backend.cpp` менять МОЖНО только добавлением (параметризация
  prefetch-инфры), существующее поведение MoE expert-prefetch ломать
  нельзя.
- kvarn-путь без `--kv-hot-size` (флаг не задан / 0) обязан работать
  РОВНО как сейчас — фича строго opt-in, дефолт поведение не меняет.
- Чужого WIP в дереве нет (всё закоммичено, HEAD `d3680c912`) — но
  turbo-код (ggml-turbo-quant.c, WHT в graph) не трогать.
